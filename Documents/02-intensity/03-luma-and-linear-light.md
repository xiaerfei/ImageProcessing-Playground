## 零、先给结论

| 你在做的事 | 该用哪个「亮度」 |
| :--- | :--- |
| 学 Gonzalez、写图像算法 | **Luma**(`cv2.cvtColor(BGR2GRAY)`),别多想 |
| 处理视频帧、YUV 数据 | **Luma**,Y 平面本来就是它 |
| 缩放、模糊、混合图层 | 严格说该用**线性光**,但全行业都在编码域做 |
| 判断两个颜色差多少 | **L\***(CIE Lab),论文里的 ΔE 就是它 |
| 把 Y 显示到屏幕上 | 抄三份 R=G=B=Y,即 U=V=128 的 YUV→RGB(第六节) |
| 结果和别人对不上 | 依次查:权重标准、取值范围、通道顺序 |

## 一、「亮度」是三个东西

这就是这个话题容易绕晕的根源 —— 中文都叫「亮度」,英文是三个词,含义差得很远。

| 名字 | 是什么 | 用在哪 |
| :--- | :--- | :--- |
| **Luminance** `Y` | 真实的物理光强,和光子数成正比 | 物理正确的混合、HDR |
| **Luma** `Y′` | 对**编码后**的 R′G′B′ 加权得到的近似 | 视频、图像处理,99% 的场合 |
| **Lightness** `L*` | 人眼**觉得**多亮(感知均匀) | 色差 ΔE、Lab 色彩空间 |

注意 Luma 那一撇(`Y′`,读 Y-prime)。它不是装饰,是在提醒你:
**这是编码域的值,不是物理量**。

`cv2.cvtColor(BGR2GRAY)` 给你的、YUV 里的 Y、视频里的亮度分量 —— 全都是第二个。

## 二、从 RGB 怎么算亮度

```python
Y = 0.299·R + 0.587·G + 0.114·B      # Rec.601
```

### 为什么不是 (R+G+B)/3

因为人眼对三种颜色的敏感度差得远 —— 视网膜里感绿的视锥细胞最多。
同样物理强度的绿光,看起来比蓝光亮好几倍。

实测:在随机彩色像素上,**简单平均与 Rec.601 平均差 20.39,最大差 63.3**;
即使在低饱和为主的真实照片上,也有平均 5.22、最大 20.2 的差距。
一片纯绿会被严重低估,一片纯蓝会被高估。简单平均是明确的错误,不是「近似」。

### 三套权重

| 标准 | R | G | B | 用在 |
| :--- | ---: | ---: | ---: | :--- |
| Rec.601 | 0.2990 | 0.5870 | 0.1140 | SDTV、JPEG、**OpenCV 默认** |
| Rec.709 | 0.2126 | 0.7152 | 0.0722 | HDTV、sRGB |
| Rec.2020 | 0.2627 | 0.6780 | 0.0593 | UHD、HDR |

实测 601 与 709 的差距:随机像素上**平均 9.74,最大 31.4**;
在真实照片(coffee.png)上**平均 4.86,最大 12.8** —— 自然照片里高饱和色少,
差距比最坏情况小一截。

不算大,但足以让你在对比算法时怀疑人生。**关键是全程用同一套**。

`cv2.cvtColor(BGR2GRAY)` 实测就是 **Rec.601 + 全范围(0~255)**,
与手算 `0.299R+0.587G+0.114B` 最大差 1(四舍五入),与 Rec.709 最大差 12.8。

要 709 得自己写:

```python
b, g, r = bgr[:,:,0], bgr[:,:,1], bgr[:,:,2]
y709 = np.clip(0.2126*r + 0.7152*g + 0.0722*b, 0, 255).astype(np.uint8)
```

## 三、Luma:将错就错的近似

### 错在顺序

做音视频的最好懂的类比是**分贝**。

两个 60 dB 的声音叠加是多少?**不是 120 dB,是 63 dB。**
因为 dB 是对数刻度,不能直接相加 —— 必须先转回线性功率,加完,再转回 dB。

**gamma 编码之于光强,和 dB 之于声功率是同一回事**:都是把线性的物理量
压成非线性的感知刻度。

现在看两种算法的区别,注意顺序:

```
真亮度 Luminance:  R′G′B′ ──解码──▶ 线性光 ──加权──▶ Y ──编码──▶ 灰度
                   (先把「分贝」转回「功率」,加完再转回来)

  Luma     Y′    :  R′G′B′ ─────────── 加权 ───────────▶ Y′
                   (直接把三个「分贝值」加权平均)
```

**Luma 就是「把三个声道的 dB 值直接加权平均当作总响度」。**

数学上没道理:gamma 是条弯曲线,加权平均是直的操作,
弯的和直的换顺序,结果就不一样。

### 错多少

```
颜色              R,G,B      Luma     真实亮度        差
─────────────────────────────────────────────────────────
纯红        (255, 0, 0)      54.2       127.1     +72.9
纯蓝        (0, 0, 255)      18.4        76.0     +57.6
品红      (255, 0, 255)      72.6       145.4     +72.8
纯绿        (0, 255, 0)     182.4       219.9     +37.6
─────────────────────────────────────────────────────────
中灰    (128, 128, 128)     128.0       128.0      +0.0
肤色    (222, 184, 155)     190.0       191.1      +1.1
暗绿       (34, 80, 40)      67.3        70.6      +3.3
```

纯红差了 **73** —— Luma 说它是 54(很暗),按真实光强该是 127(中灰)。
纯蓝差 58,接近 4 倍误差。

但下半部分:**中灰误差 0,肤色 1.1,暗绿 3.3**。

### 为什么还在用

**历史原因**:1953 年 NTSC 彩色电视要兼容已有的黑白电视机 —— 黑白机只认一路
信号,所以彩色信号必须能算出一个「亮度」给它。

那是**真空管电路**的年代。gamma 是幂运算,对 R、G、B 各算一次模拟电路做不起。
而摄像机端为了传输本来就要做一次 gamma 编码。于是工程师选了最省的路:
**编码完直接加权求和** —— 三个乘法一个加法,电阻网络就能实现。

**现实原因**:看上表的下半部分。真实照片里绝大多数像素是低饱和度的 ——
皮肤、墙、天空、木头、草地,误差都在个位数,肉眼看不出。
只有纯饱和色才崩,而那种颜色在自然照片里几乎不存在。

这个缺陷有正式名字:**constant luminance failure**(恒定亮度失效)。
Rec.2020 专门定义了 `Yc′CbcCrc` 来修它,但基本没人用 —— 整个产业链
都建立在旧的那套上了。

## 四、线性光为什么不直接用

**线性光**就是和光子数成正比的物理量:光强翻倍,数值就翻倍。
听起来这才是唯一正确的表示法,那为什么全世界的图片都不这么存?

### 答案:8 bit 装不下

人眼对暗部的分辨力远强于亮部。同样是差 1% 的亮度,在暗处一眼看出,
在亮处根本察觉不到。

于是问题变成:**256 个码值,该怎么分配给 0~100% 的光强?**

**线性存储**的分法是「平均分」—— 每档都是 1/255 的光强。实测后果:

```
     光强        线性 8bit 的一档     sRGB 8bit 的一档
    0.1%            392.2%  ←看得出        33.3%  ←看得出
    1.0%             39.2%  ←看得出         6.3%  ←看得出
    5.0%              7.8%  ←看得出         3.1%  ←看得出
   21.6%              1.8%  ←看得出         1.7%  ←看得出
   50.0%              0.8%                  1.2%  ←看得出
  100.0%              0.4%                  0.9%
```

> 注意这张表是按**光强**比的,不是按码值比 —— 同一个码值在两种编码下
> 对应的光强完全不同(线性码值 16 是 6.3% 光强,sRGB 码值 16 只有 0.5%),
> 按码值比是不公平的。人眼大约 1% 就能看出台阶。

在 0.1% 光强处,线性的**一档就跳 392%** —— 亮度差了近 5 倍,
中间没有任何过渡。暗部渐变必然出现一道道色带。

换个角度看码值花在哪:

```
       光强区间          线性给      sRGB 给
      最暗的 1%           3 档        26 档
      最暗的 5%          13 档        64 档
  暗部到中灰(21.6%)      56 档       129 档
      最亮的一半         128 档        68 档
```

**线性把一半码值(128 档)扔给了最亮的一半光强** —— 而那里人眼最不敏感,
0.8% 的台阶根本看不出来,纯属浪费。最暗的 1% 只剩 3 档。

sRGB 编码做的事,就是**把码值从亮部挪到暗部**。

### 那要多少 bit 才够

要求全范围内相邻码值的亮度差都不超过 1%:

```
  黑位定在 1/100  最大亮度   →     10,000 档 = 13.3 bit
  黑位定在 1/1000(普通暗部) →    100,000 档 = 16.6 bit
  黑位定在 1/10000(HDR)     →  1,000,000 档 = 19.9 bit

  sRGB 8bit(256 档)覆盖同样范围
```

**所以结论不是「线性不好」,而是「8 bit 装不下线性」。**

反过来看就清楚了 —— **位深一够,大家立刻就用线性**:

| 场合 | 存储 | 位深 |
| :--- | :--- | :--- |
| 相机 RAW | **线性** | 12~14 bit |
| 渲染引擎、合成软件内部 | **线性** | float16 / float32 |
| PNG / JPEG / 视频 | gamma 编码 | 8 bit |
| HDR 视频 | PQ / HLG 曲线(也是感知编码) | 10~12 bit |

### 顺带一个历史巧合

CRT 显像管的电子枪有个物理特性:**输出光强 ≈ 输入电压的 2.2 次方**。

这和 sRGB 的编码曲线正好互为反函数。所以在 CRT 时代,
摄像机端做 gamma 编码 → 传输 → 显像管的物理特性自动解码,
**整条链路不需要任何额外计算**,而且顺带获得了感知编码的好处。

CRT 早没了,但 gamma 保留了下来 —— 因为「省码值」这个理由从来没有失效。
现在的 LCD/OLED 内部反而要**主动模拟**这条曲线。

## 五、YUV:亮度已经在那儿了

好消息:**YUV 格式不用算亮度,Y 平面本身就是**。
`yuv420p` 的前 `W×H` 个字节就是一张完整分辨率的灰度图:

```python
data = np.fromfile("video.yuv", dtype=np.uint8)
y = data[:w*h].reshape(h, w)          # 这就是亮度图
```

### 为什么要转 YUV

两个理由,都和「亮度」这个话题直接相关:

1. **兼容黑白电视** —— 历史理由,见第三节
2. **色度子采样** —— 现实理由,也是整个视频压缩的地基

人眼对**亮度**的分辨力远高于**色度**。把 Y 保持全分辨率、
UV 各方向减半(4:2:0),数据量直接少掉一半,肉眼几乎看不出区别。

RGB 做不到这一点 —— 三个通道里都混着亮度信息,砍哪个都会糊。
必须先把亮度**分离出来**,才能对剩下的部分下手。

实测验证:16×16 的 `yuv420p` 文件是 **384 字节** = Y 256 + U 64 + V 64。

### 陷阱:limited range

实测(用 ffmpeg 转纯色图后直接读第一个字节):

```
             yuv420p(limited)    yuvj420p(full)
纯白    Y =       235                255
纯黑    Y =        16                  0
纯红    Y =        81                 76
```

`yuv420p` 是 **limited range**(又叫 TV range / video range):
**黑是 16 不是 0,白是 235 不是 255**。两头留出的余量是给信号过冲用的历史遗留。

这意味着:**从视频里抠出的 Y 平面,直接当 0~255 用就是错的**。
全黑画面你会读到 16,做直方图发现左边空一截,算对比度偏小。

那个红色的 81 正好验证转换公式:

```
full range 的 76  →  16 + 219 × (76/255) = 81.3  →  81 ✓
```

互转:

```python
y_full    = np.clip((y_limited.astype(np.float64) - 16) * 255/219, 0, 255).astype(np.uint8)
y_limited = (y_full.astype(np.float64) * 219/255 + 16).astype(np.uint8)
```

怎么判断手上的是哪种:

```bash
ffprobe -v error -show_entries stream=pix_fmt,color_range -of default=nw=1 input.mp4
```

- `pix_fmt=yuv420p` + `color_range=tv`(或为空)→ limited
- `pix_fmt=yuvj420p` 或 `color_range=pc` → full(`j` 就是 JPEG 的 j)

**OpenCV 这边全是 full range**,实测纯白 → Y=255。
所以 `cv2.cvtColor(BGR2YUV)` 的结果和 ffmpeg 的 `yuv420p` **不是一回事**,
两边数据混用必错。

## 六、Y 怎么显示回屏幕

算出 Y 之后会冒出一个很自然的疑问:**屏幕怎么显示一张单通道的图?**

答案是显示不了。**屏幕根本不认识「灰度图」这种东西** —— 每个像素物理上就是
红绿蓝三颗灯,你必须给它三个数。所以任何一张 Y 图在真正点亮之前,
一定有某一层代码把它变回了三个数。

### 变回去只做一件事

R = G = B = Y。亮度 200 的像素 → 红灯 200、绿灯 200、蓝灯 200 →
三色等量混合 → 中性灰。没有任何矩阵运算。

### 抄三份就是 YUV→RGB

这不是近似,也不是偷懒。BT.601 全范围的反变换是:

```
R = Y + 1.402 (V-128)
G = Y - 0.344 (U-128) - 0.714 (V-128)
B = Y + 1.772 (U-128)
```

灰度意味着**没有色度**,也就是 U = V = 128(8 bit 下 128 才是「零」,不是 0)。
代进去括号里全是 0,三条式子当场坍缩成 `R = G = B = Y`。

实测(把 Y 和中性色度组成真正的 YUV,走完整矩阵,对比直接抄三份):

```python
import cv2, numpy as np
y = np.array([[0, 64, 128, 200, 255]], np.uint8)
print(cv2.cvtColor(y, cv2.COLOR_GRAY2BGR).reshape(-1, 3).tolist())
yuv = np.dstack([y, np.full_like(y, 128), np.full_like(y, 128)])
print(cv2.cvtColor(yuv, cv2.COLOR_YUV2RGB).reshape(-1, 3).tolist())
```

```
GRAY2BGR:          [0,0,0] [64,64,64] [128,128,128] [200,200,200] [255,255,255]
YUV(U=V=128)→RGB:  [0,0,0] [64,64,64] [128,128,128] [200,200,200] [255,255,255]
```

逐值相同。**「抄三份」是色度为中性时 YUV→RGB 的精确解。**

这也解释了编码那边的常规操作:要把一路彩色视频变成黑白,
不用动 Y 平面,把 U/V 两个平面整个填 128 就行。

### matplotlib 里是谁干的

```python
ax.imshow(img, cmap="gray", vmin=0, vmax=255)
```

`cmap="gray"` 就是这张查找表,内容恰好是 `v → (v, v, v)`。

`vmin/vmax` 为什么**必须显式给**:matplotlib 查表前要先把数归一化到 0~1。
不给范围,它就拿这张图自己的 min/max 去归一化 —— 一张实际范围 [11, 236] 的图,
11 会被拉成纯黑、236 拉成纯白,**悄悄给你拉了一次对比度**,
你看到的就不再是 Y 本身了。写死 `vmin=0, vmax=255` 才是「所见即所存」。

`cv2.imshow` 对单通道图做同样的事,只是固定按 0~255,不给你选的余地。

### 什么时候「抄三份」会出错

前提是:**算 Y 用的那些 R、G、B 本身就是 gamma 编码后的值**。

`cv2.imread` 读进来的 JPEG 像素是 sRGB 编码值,算出来的是 **Luma Y′**,
送回屏幕时屏幕再按 gamma 解码 —— 编码和解码配套,一进一出,对上了。

但如果先转**线性光**再算亮度(那是真 Luminance,权重也变成
0.2126/0.7152/0.0722,见第四、七节),就**不能直接抄三份送显示**,
必须先重新做 gamma 编码。漏了这步图会明显偏暗:
中灰 0.5 线性光编码后该是 188 左右,直接送 128 过去,暗一大截。

> 换句话说,Y′ 和 Y 不只是权重不同,**它们活在不同的域里,
> 显示路径也不一样**。这是第三节「错在顺序」在显示端的镜像。

> **跑得出来的版本**:[`Ch03_Spatial_Filtering/04_gamma_transform.py`](../../Python-Prototyping/Ch03_Spatial_Filtering/04_gamma_transform.py)
> 的实验 ⑧⑨ 把这条链实测了一遍 —— 对已编码的图做 γ=2.2 就是解回线性光
> (中灰 128 的线性光只有 21.6%),屏幕还会再解一次,所以看着「黑了两遍」;
> 解码后重新编码则与原图逐像素相同。实验 ⑨ 用黑白条纹缩小量化了域搞错的代价:
> 编码域算出 128,线性域算出 **188**,差 60 个灰阶。

## 七、什么时候真该切到线性

如果你要做的事情是**物理正确**的 —— 比如「亮度提高一倍」真的指光子数翻倍:

```python
def srgb_to_linear(c):          # c 是 0~1
    return np.where(c <= 0.04045, c/12.92, ((c+0.055)/1.055)**2.4)

lin = srgb_to_linear(rgb/255.0)
Y = 0.2126*lin[...,0] + 0.7152*lin[...,1] + 0.0722*lin[...,2]   # 真 luminance
```

严格说,**缩放、模糊、混合图层都该在线性域做**。最经典的例子:
把黑白相间的细条纹缩小,在编码域做会得到偏暗的灰,在线性域做才是正确的中灰。

但现实是整个行业(包括 Photoshop 默认)都在编码域直接做 —— 快,而且
大多数时候看不出来。知道有这回事,遇到问题时知道去哪找就够了。

> 顺带:`sRGB 的 128 只对应 21.6% 的线性光` —— 这个数字在 [03-contrast.md](../03-histogram/03-contrast.md)
> 里出现过。中灰看起来在黑白正中间,物理上却只有五分之一的光,
> 这正是人眼非线性的直接体现,也是 gamma 编码「碰巧好用」的原因。

## 八、排查清单

亮度算出来不对,按这个顺序查:

| 症状 | 十有八九是 |
| :--- | :--- |
| 和别人的灰度图差几个到十几 | 权重标准不同(601 / 709) |
| 和别人的灰度图差 1,且约一半像素都差 | 落回 uint8 时用了截断,忘了四舍五入 |
| 全黑画面的亮度不是 0 而是 16 | limited range 没转换 |
| 红蓝颠倒 | OpenCV 是 BGR |
| 灰度图偏色/偏暗 | 用了 `(R+G+B)/3` |
| 大面积纯色(霓虹、LED 屏、纯色 UI)结果诡异 | Luma 在高饱和色上的固有误差 |
| 缩放后的细条纹整体变暗 | 该在线性域做却在编码域做了 |
| 灰度图显示出来整体偏暗 | 在线性域算完 Y 就直接送显示,漏了 gamma 编码 |
| 灰度图显示出来对比度比原图强 | `imshow` 没给 `vmin/vmax`,被按图内 min/max 拉伸了 |
