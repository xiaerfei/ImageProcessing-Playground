# 取整与浮点 —— 小数落回 uint8 的三条规矩

算图像的时候,**小数是躲不掉的**:`0.299R + 0.587G + 0.114B` 几乎不可能算出整数,
缩放、旋转、滤波、伽马,每一步都在造小数。但 8bit 图像只能存 0~255 的整数。
这中间的「落地」动作,是图像处理里最容易出问题、又最少被讲的一环。

一句话先给结论:

> **中间全程 float,只在最后落一次地;落地写成
> `np.clip(np.rint(x), 0, 255).astype(np.uint8)`,三件事一个都不能少。**

`rint` 防单向偏置,`clip` 防回绕,顺序不能换。下面逐条说为什么。

文中所有数字由 `Python-Prototyping/Ch01_02_Fundamentals/01_rounding_rules.py` 实测算出,
跑一遍就能复现。

---

## 规矩一:要落回整数,就四舍五入,别截断

`astype(np.uint8)` 是**向下取整**:129.1 → 129,129.9 也 → 129。

关键不在「差多少」,而在**差的方向**。小数部分大致均匀分布在 0~1 之间,
所以截断**平均每次少 0.5,而且永远是少**。这不叫误差,这叫**偏置(bias)**
—— 单向的、会累积的。四舍五入则有时多 0.5、有时少 0.5,**平均为 0**。

实测 100 万个 0~255 的随机小数:

| 做法 | 平均误差 |
| :--- | ---: |
| 截断 `astype(np.uint8)` | **−0.4999**(永远 ≤ 0) |
| 四舍五入 `np.rint` | −0.0002(正负抵消) |

一次少 0.5 看着无所谓,重点是它**攒得起来**。见规矩二。

---

## 规矩二:中间结果不要落回 uint8

这条比「怎么取整」更重要。

实测:对 0~255 每个灰阶做 20 轮「×1.1 再 ÷1.1」,理论上应该原样返回:

| 做法 | 平均偏移 | 最大偏移 | 被改变的灰阶 |
| :--- | ---: | ---: | ---: |
| 每步截断落回 uint8 | **−13.56** | 43 | 245/256 |
| 每步四舍五入落回 uint8 | −1.08 | 23 | 23/256 |
| **全程 float,最后落一次** | **+0.00** | **0** | **0/256** |

截断跑 20 轮,整张图平均暗了 13 个灰阶 —— **肉眼可见地发灰发暗**。
而四舍五入虽然好得多,也仍然有 −1.08:**取整做得再好,做 20 次也扛不住**。

根本解法不是把取整做得更精细,是**只做一次**:

```python
img = img.astype(np.float32) / 255.0                            # 进:一次性抬到浮点
...                                                              # 中间全程 float
out = np.clip(np.rint(img * 255.0), 0, 255).astype(np.uint8)    # 出:只落一次
```

这就是专业调色/合成软件内部跑 16bit 或 32bit float 的理由 ——
不是为了「更精确」,是为了**中间不落地**。

> 对做视频滤镜链的人尤其要紧:每个 filter 都 uint8 进、uint8 出,
> 五六个串起来偏色就出来了,而且每一个单独测都「看不出问题」。
> 要么整条链统一在 float 上跑,要么接受这份累积偏差。

### float32 还是 float64

图像处理用 **float32 就够**:8bit 源数据只有 256 档,float32 有 24bit 尾数,
中间过程再怎么算也远没到精度不够的时候。float32 内存减半、SIMD 吞吐翻倍,
GPU 那边更是只认 float32(乃至 float16)。

float64 留给**统计类**的场合 —— 比如全图求和、算方差,几百万个数累加时
float32 的尾数会开始吃不消。

## 规矩三:落回整数时要「饱和」,不要「回绕」

这条会造出真正诡异的 bug。

```python
np.array([-1, 0, 255, 256, 300], np.int16).astype(np.uint8)
→ [255, 0, 255, 0, 44]
```

**300 变成了 44,−1 变成了 255**。numpy 的 `astype` 对越界值是**取模回绕**
(300 % 256 = 44),不是截断到边界。

后果很具体:**你把图提亮,过曝的地方不会变白,而会变成一块块黑斑**。
减暗时则是暗部冒出白点。第一次遇到时几乎不可能猜到原因。

C/OpenCV 那边有 `saturate_cast`,行为是饱和(300 → 255,−1 → 0),
所以 `cv2.add` 之类不会出这个问题。**numpy 没有对应物,必须自己 clip**:

```python
np.clip(value, 0, 255).astype(np.uint8)    # clip 一定要在 astype 之前
```

顺序不能反 —— 先 `astype` 就已经绕完了,再 clip 也救不回来。

## 那个恰好 .5 的值往哪边走

`np.rint` / `np.round` 用的是**银行家舍入**(round-half-to-even),.5 往**偶数**靠:

```python
np.rint([0.5, 1.5, 2.5, 3.5])  →  [0, 2, 2, 4]
```

不是直觉的「0.5 一律进位成 1」。为什么这么设计?因为「逢 .5 一律进位」
本身也是个单向偏置 —— 又回到规矩一的问题。往偶数靠能让这部分误差也正负抵消。

实践上**图像处理里基本不用管**:恰好落在 .5 的像素极少,
两种做法在实验 4 里的差别是 241 个像素 vs 231 个像素。
知道有这回事,别在单元测试里写死 `round(0.5) == 1` 就行。

## 工业实现:干脆不用小数

OpenCV 内部算灰度大致是这样(整数定点):

```c
(R*19595 + G*38470 + B*7471 + 32768) >> 16
```

- `19595` = `0.299 × 65536` 取整 —— 把小数系数「放大 65536 倍」变成整数
- `>> 16` = 除以 65536,把倍数还回来
- **`+ 32768` 就是四舍五入**:32768 = 65536/2,**加上半个单位再向下取整,
  等价于四舍五入**

最后这个技巧到处都是。你在 ffmpeg、编解码器源码里会反复看到
`+ (1 << (shift - 1))`,看到就知道是在做 rounding,不是什么魔法常数。

为什么用定点而不用浮点:整数运算快,更重要的是**跨平台逐位可复现** ——
浮点在不同 CPU、不同编译优化下可能差最后一位,编解码器绝不能容忍
(解码端算出来和编码端差一位,误差会顺着帧间预测一路滚雪球)。

### 别指望和 OpenCV 逐像素相同

实测手写实现和 `cv2.cvtColor(BGR2GRAY)` 的差距:

| 手写实现 | 随机噪声图上的不一致像素 | 最大差 |
| :--- | ---: | ---: |
| 整数定点 shift16 | 215 / 160000 (0.13%) | 1 |
| 浮点 + `np.rint` | 241 / 160000 (0.15%) | 1 |
| 浮点 + `np.rint`(换成 lenna 真实照片) | **0** | **0** |

结论:**差异上限是 ±1 个灰阶,在自然照片上常常一个都不差,但不保证**。
cv2 内部走的是整数定点 + SIMD,取整细节和 numpy 的浮点路径不完全同步。

写验证代码时,断言要写成「最大差 ≤ 1」,不要写「完全相等」——
换一张图、换一个 OpenCV 版本就可能挂。

## 什么时候反而该用向下取整

不是所有场合都该四舍五入。判据是:
**这个小数代表「数值」还是「位置」?**

| 场景 | 该用 | 为什么 |
| :--- | :--- | :--- |
| 算出的像素值落回 8bit | **四舍五入** | 小数是数值,要最近的那一档 |
| 直方图分 bin | **floor** | 值 7.9 属于第 7 号 bin,不是第 8 号 |
| 数组索引、最近邻采样取坐标 | **floor** | 索引要和格子一一对应 |
| 双线性插值的权重 | **不取整** | 小数部分本身就是权重,取整就没插值了 |

混淆这两类是常见 bug:拿 `round` 去算 bin 号,会让第 0 号和最后一号 bin
只有一半宽度,直方图两端莫名其妙地矮一截。

## 排查清单

| 症状 | 十有八九是 |
| :--- | :--- |
| 滤镜链跑完整体发暗/发灰 | 中间反复落回 uint8,而且用的是截断 |
| 提亮后高光处出现黑斑 | `astype(np.uint8)` 回绕,忘了先 clip |
| 减暗后暗部出现白点 | 同上,负值绕成了 255 |
| 和 OpenCV 差 1,但只差一点点像素 | 正常,定点 vs 浮点的取整差异 |
| 和 OpenCV 差 1,且一半像素都差 | 忘了 `np.rint`,在做截断 |
| 直方图第一根和最后一根柱子偏矮 | 分 bin 用了 round,该用 floor |
| 反复缩放后图像越来越糊/越来越暗 | 每次缩放都落回 uint8 了 |
